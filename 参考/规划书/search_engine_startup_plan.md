# 自有搜索引擎创业方案

## 一、项目定位

**目标：** 面向研究者、开发者和深度信息用户，先做一个拥有独立索引、独立排序、可追溯证据的垂直搜索引擎，再逐步扩展成通用搜索产品。

工作名称：**OpenTrace**。这只是方案中的代号，不代表已完成商标或域名核查。

### 产品战略

- **自有索引：** 掌握抓取、存储、更新与去重。
- **自有排序：** 掌握召回、相关性与排序逻辑。
- **证据与发现：** 帮用户找到可验证的信息，并发现热门排名之外的优质内容。
- **持续改进：** 用真实搜索问题和评估反馈优化结果。

核心原则：可以借助开源软件和第三方数据源，但索引数据、排序规则、评估体系和产品体验要逐渐掌握在自己手中。

## 二、第一阶段目标用户

建议从**开发者与技术研究搜索**切入，优先覆盖：

- 官方技术文档和 API 参考
- 开源项目文档、仓库信息与公开讨论
- 技术博客和独立开发者文章
- 错误日志、框架版本、技术实现和兼容性问题

### 为什么从这里开始

1. 目标内容范围相对明确，不必一开始覆盖整个互联网。
2. 用户经常遇到具体问题，搜索质量容易通过真实任务验证。
3. 技术用户可以提供相对高质量的早期反馈。
4. 可以逐步建设自己的抓取与索引系统，而不是完全依赖第三方搜索 API。

第一阶段不是证明能搜索所有内容，而是证明：针对一类真实问题，能更稳定地找到值得阅读的资料。

## 三、产品差异化

### 功能 A：技术问题专搜

支持搜索错误日志、API 名称、框架版本、开源项目、技术文档和真实讨论。

优先精确匹配技术术语、版本号、报错信息和代码标识符，避免语义相似但实际不相关的页面排在前面。

### 功能 B：可解释的搜索排序

结果可以说明为什么排在当前位置，例如：

- 精确匹配了报错信息
- 来自对应版本的官方文档
- 解决了相同问题的真实讨论
- 内容较新，且没有被重复页面挤占排名

### 功能 C：发现热门排名之外的答案

在主结果之外，发现独立博客、小型开源项目、冷门技术讨论和不同解决方案。目标不是把低质量网页推到前面，而是让高质量的非热门内容获得合理展示。

### 产品承诺

> 搜得准，找得到，能验证，还能发现你原本找不到的资料。

精确检索是基本盘，可解释排序是技术资产，独特内容发现则是吸引用户的特色。

## 四、技术架构

第一版建议采用一台服务器、一个搜索引擎和一套轻量抓取程序。先建立完整检索闭环，不急于引入分布式计算、复杂消息队列或自训练大模型。

```text
数据源
  ├─ 官方文档
  ├─ 开源项目
  ├─ 技术博客
  └─ 公开讨论
       ↓
抓取与内容处理
  ├─ URL 发现
  ├─ robots.txt 检查
  ├─ 正文提取
  ├─ 去重
  └─ 更新检测
       ↓
自己的文档库与索引
  ├─ 规范化文档
  ├─ 来源元数据
  ├─ 版本与抓取时间
  └─ 内容指纹
       ↓
自有检索与排序层
  ├─ BM25
  ├─ 字段权重
  ├─ 过滤
  ├─ 结果融合
  ├─ 质量排序
  └─ 域名去重
       ↓
搜索产品
  ├─ 结果列表
  ├─ 代码高亮
  ├─ 筛选器
  ├─ 来源解释
  └─ 可选 AI 摘要
```

### 推荐技术栈

| 模块 | 第一版建议 | 说明 |
|---|---|---|
| 后端 API | Python + FastAPI | 开发快，适合抓取与检索实验 |
| 网页抓取 | Scrapy | 方便控制抓取范围、限速和重试 |
| 正文提取 | Trafilatura 等 | 去除导航、广告等页面噪声 |
| 搜索引擎 | OpenSearch | 支持全文索引、BM25 和后续混合搜索 |
| 元数据 | PostgreSQL | 保存 URL、来源、版本、更新时间和抓取状态 |
| 前端 | Next.js | 构建搜索结果页和响应式界面 |
| 部署 | Docker + 单台 VPS | 简单、便于迁移和控制成本 |

**重要取舍：不要从零编写倒排索引。** 应该掌握自己的索引数据、抓取策略、文档结构、相关性特征、排序逻辑和评估数据；底层可以使用成熟的开源搜索引擎。后续如有需要，再研究 Lucene 或替换特定模块。

## 五、自有排序方案

先使用可调节的排序公式建立基线，而不是一开始就训练复杂的机器学习模型。

\[
S(q,d)=w_1L+w_2F+w_3V+w_4R+w_5Q
\]

其中：

- **L：** BM25 文本相关性
- **F：** 标题、URL、代码符号、版本号等字段的精确匹配程度
- **V：** 语义相关性，可在第二阶段加入
- **R：** 时效性，根据查询是否需要最新信息动态调整
- **Q：** 来源与页面质量，例如正文完整度、重复程度和来源类型

这些权重是待实验调整的参数，不是已验证的最佳值。实际实现时需要进行分数归一化，避免不同模型的分值无法直接比较；也可以使用倒数排名融合（RRF）合并关键词和语义检索的候选结果。

技术搜索尤其要注意：**精确匹配不能轻易被语义相似度压下去。** 搜索具体报错时，真正匹配该错误的页面应该优先于只在语义上相似的其他错误。

## 六、自有索引的数据来源

建议分三个层次建设：

1. **明确选择的站点：** 官方文档、开源项目文档、公开技术博客和允许抓取的讨论页面。
2. **相关链接扩展：** 从已收录页面发现新 URL，通过域名白名单、抓取深度、限速和质量规则控制增长。
3. **公开网页数据集：** 当抓取与索引流程成熟后，再研究 Common Crawl 等公开语料。此类语料是原始数据来源，不是开箱即用的高质量搜索结果库。

务必遵守站点的抓取规则、服务条款和适用法律，合理限速，并尊重删除与更新要求。“公开可访问”不等于可以无限制复制和展示。

## 七、MVP 范围

初期可将约 **20–50 个高价值技术站点**作为试验范围，目标收录 **1 万至 10 万篇有效文档**。这只是工程实验规模，不代表市场竞争力指标。

### 必须完成

- 自有抓取任务与 URL 队列
- 正文提取、规范化和重复内容识别
- 自己的文档库和全文索引
- 搜索框、结果页、分页与基本筛选
- 自定义 BM25 字段权重和精确匹配规则
- 保存测试查询、人工标注相关结果
- 搜索日志与简单错误监控

### 验证有效后再做

- 向量语义检索和混合排序
- AI 答案与原文证据引用
- 用户个性化排序
- 持续追踪和邮件通知
- 复杂反垃圾模型与分布式索引

第一版甚至不必接入大模型。先把关键词搜索、精确匹配和结果质量做扎实。只有发现关键词检索确实遗漏了大量有价值的结果时，再加入语义检索。AI 摘要不是早期重点，因为如果检索层没有找到正确原文，摘要再漂亮也无法弥补。

## 八、90 天执行计划

### 第 1–2 周：验证问题

- 收集 100 个真实的技术搜索问题。
- 访谈 5–10 位目标用户，了解其当前搜索习惯。
- 选择 20–50 个目标站点，检查抓取规则和内容结构。
- 用现有搜索引擎建立基准结果，记录有用页面。

**交付物：** 问题集、站点清单、相关性评估表。

### 第 3–4 周：建立索引

- 开发抓取、正文提取和增量更新程序。
- 将文档写入自己的存储层和搜索索引。
- 实现标题、正文、URL、来源、时间和内容指纹等字段。
- 建立可查询、可重建、可检查的数据管道。

**交付物：** 一个能持续更新的垂直搜索索引。

### 第 5–8 周：打造排序

- 建立 BM25 基线。
- 加入技术符号、标题、版本、精确短语等特征。
- 对重复页面进行聚合或降权。
- 加入域名多样性和按查询意图调整的时效性。
- 对不同排序版本进行离线对比。

**交付物：** 有实验数据支撑的第一版自有排序系统。

### 第 9–12 周：真实测试

- 上线简洁的搜索网站。
- 邀请 20–50 名开发者试用。
- 记录查询、点击、无结果搜索和用户主动反馈。
- 根据真实问题修正索引覆盖和排序。
- 根据数据决定是否接入语义检索和 AI 摘要。

**交付物：** 公开测试版本、评估报告和下一阶段优先级。

## 九、搜索质量评估

不要只凭主观感受判断搜索质量。建立固定评估集，每次调整排序都重新测试。

| 指标 | 作用 |
|---|---|
| Recall@20 | 相关结果是否被找出来 |
| NDCG@10 | 高质量结果是否排在前面 |
| MRR | 用户最先找到有用结果的速度 |
| 无结果率 | 哪些查询暴露了索引缺口 |
| P95 延迟 | 绝大多数查询是否足够快 |

先记录当前排序基线，再争取在同一批测试查询上取得可重复的提升。不要随意设定没有依据的漂亮百分比。

还要按查询类型分别评估：精确错误信息、概念解释、版本兼容和项目选型。总体分数可能掩盖某一类查询的明显退步。

## 十、商业模式

初期不建议依赖广告变现。广告容易干扰排序目标，也会让项目过早追逐流量，而不是搜索质量。

### 阶段 1：免费搜索，验证产品价值

- 免费开放基础搜索。
- 观察用户是否愿意用它替代部分现有技术搜索。
- 建立搜索质量、使用频率和回访数据。

### 阶段 2：专业版订阅

验证有人愿意付费后，再测试专业功能：

- 批量研究
- 长时间追踪
- 保存搜索工作区
- 进阶过滤
- 更高额度的 AI 研究功能

可先测试每月 **5–15 美元**的价格区间，再根据真实付费转化和使用成本调整。这只是实验定价，不是已验证的市场价格。

### 阶段 3：搜索 API 与企业服务

在拥有稳定索引和相关性优势后，考虑提供：

- 开发者搜索 API
- 私有文档搜索
- 内部知识检索
- 定制索引服务

## 十一、成本与资源规划

初期尽量控制固定成本，把资源花在抓取稳定性、索引存储和测试上。

| 项目 | 初期建议 |
|---|---|
| 域名 | 普通域名即可 |
| 服务器 | 一台低配 VPS，先压测再扩容 |
| 数据库 | 尽可能使用同一台机器或低成本实例 |
| AI 模型 | 前期可不接入，后期按需调用 |
| 向量索引 | 验证关键词搜索后再加入 |
| 监控和日志 | 先使用轻量、低成本方案 |

个人验证阶段可以尝试把基础设施控制在每月几十美元的量级，但这不是保证。数据量、磁盘、内存、抓取带宽、备份和 AI 调用都可能增加成本。不要因为公开网页数据可以免费获取，就误以为处理大规模网页的成本也很低。

建议设置预算红线：在没有验证搜索质量之前，不购买昂贵 GPU、不搭建多节点集群，也不运行大规模全网抓取。

## 十二、长期技术护城河

搜索引擎的长期价值不只是文档数量，而是四种资产的积累：

1. **独特且持续更新的索引：** 收录范围、更新速度、原始资料识别和小众来源覆盖。
2. **自己的相关性评估数据：** 哪些结果真正解决了问题，哪些只是关键词匹配，哪些来源在特定查询下更可靠。
3. **持续改进的排序系统：** 把人工评估、匿名化交互信号和失败案例转化为排序规则或训练数据，并控制隐私风险。
4. **持续使用的专业用户：** 真实问题会揭示哪些内容值得收录、哪些排序错误影响最大，以及哪些功能值得付费。

最容易被忽略的是相关性评估数据。即使使用相同的开源搜索引擎和模型，更好的领域数据、更好的评估集和更有效的迭代流程，也可能逐渐形成优势。

## 十三、现在最该做的三件事

按优先级执行：

1. **选定首批技术内容范围。** 从开发者文档、开源项目资料和技术博客中选择 20–50 个站点。
2. **建立 100 个真实搜索问题的测试集。** 给每个问题记录有用结果和相关性等级，并保留现有搜索方式的基准结果。
3. **实现自己的抓取、索引和 BM25 排序。** 做出可以测量、可以重建、可以持续优化的最小搜索系统。

不要先花一个月设计 Logo、首页动画和 AI 聊天界面。搜索产品的第一张名片，是用户输入问题后看到的前十条结果。

如果这十条结果真的比用户习惯的工具更有价值，你才有理由继续扩大索引、建设语义检索和探索商业模式。

### 一个需要尽早决定的问题

第一版应该优先服务中文技术内容，还是全球英文技术内容？这会直接决定抓取来源、分词方案、索引结构和早期用户群。

- 如果还没有明确的中文用户渠道，可以先从英文开发者文档与开源项目入手。
- 如果熟悉中文开发者社区并能直接触达用户，可以优先做中文技术搜索。

两条路线都可行，但第一阶段不要同时铺开。
